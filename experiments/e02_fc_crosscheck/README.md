# E02: Cross-check of our XMI reading against ShapeChange's Feature Catalogue

- **Date:** 2026-10-14
- **Question:** Does our own XMI reader (E01) interpret the INSPIRE model the same way ShapeChange does? Do the FC and the XMI describe the same model state?
- **Why this works without Enterprise Architect:** the published Feature Catalogue is ShapeChange output. Both files say so: `<!--Feature catalogue created using ShapeChange-->` in the XML, and "This feature catalogue was generated by ShapeChange" in the HTML. Comparing against it is therefore a comparison against ShapeChange, without needing an EA licence.
- **Status:** done.

## Inputs

| File | Size | Note |
|---|---|---|
| `data/raw/approved/fc/FC_INSPIRE_v2025.1.tmp.xml` | 2.9 MB | ShapeChange's intermediate FC XML, `versionDate` 31/01/2025. It parses strictly (unlike the XMI, see E01 F1). |
| `data/raw/approved/fc/index.html` | 5.7 MB | The HTML rendering of the same content; not used |
| XMI from E01 | | same file and checksum as E01 |

## Method

[compare_fc.py](compare_fc.py) compares, per application schema, type and **own** property (no flattening on either side):
- schema: version
- type: category, abstract, supertypes
- property: name, multiplicity, voidable, value type

Results: [results/summary.txt](results/summary.txt), [results/schemas_fc_vs_xmi.csv](results/schemas_fc_vs_xmi.csv), [results/types_fc_vs_xmi.csv](results/types_fc_vs_xmi.csv), [results/props_fc_vs_xmi.csv](results/props_fc_vs_xmi.csv).

Reproduce: `cd experiments/e02_fc_crosscheck; python compare_fc.py`

## Result in one line

**Properties: 2220/2220 attributes and 202/207 association roles are identical** in name, multiplicity, voidable and value type. For the 5 test themes (AU, CP, SO, LCV, ELU): **224/224 properties identical**.

| Level | Identical | Differences |
|---|---|---|
| Schemas (in both) | 70 | 1 version difference; 20 only in the XMI; 1 only in the FC |
| Types (in both schemas) | 726 | 37 (all explained below); 1 + 2 only on one side |
| Attributes | 2220 | 0 |
| Association roles | 202 | 5 (only in MaritimeUnits, MineralResources, ProductionAndIndustrialFacilities) |

## Reader rules this experiment forced (bugs found in our reader)

Each rule was found because the comparison failed without it. They are now part of the reader.

| # | Rule | Evidence |
|---|---|---|
| R1 | An `ownedAttribute` counts as an attribute only if EA's own attribute list contains it. Some association ends are exported as `ownedAttribute` **without** the `association` marker. | EF `AbstractMonitoringObject.supersedes`, MR `EarthResource.composition` |
| R2 | Trim names. Some names in the XMI have trailing spaces, which ShapeChange removes. | `"dichloroethane "`, `"liquidHydrocarbon "`, `"EnvHealthDeterminantConcentrationMeasure "` |
| R3 | A class's category comes from the first *known* class stereotype, not simply the first stereotype. | SU `Evolution` has «voidable» + «featureType» |
| R4 | Two application-schema packages can share a name. ShapeChange appends " (2)", and we now do the same. | two "Oceanographic Geographical Features" packages (v4.0 and v3.0) |
| R5 | Association-role navigability: EA's `modifiers.isNavigable` is "false" on 382 of 385 role ends and is useless. EA's style field has three values (Navigable 1027, Unspecified 314, Non-Navigable 34). **Rule: everything except Non-Navigable is navigable.** It gives 202/207. The alternative, the standard UML rule "the role is an ownedAttribute of the class", gave only 199/207 and was rejected. | navigability tests |
| R6 | The FC writes abstract as `1`, not `true` (a bug in our FC parser, not in the model). | `<isAbstract>1</isAbstract>` |

## Findings

| # | Finding | Consequence |
|---|---|---|
| G1 | **The FC and the XMI are not from exactly the same model state**, although both are labelled v2025.1. Area Management is version **4.1 in the FC but 4.0 in the XMI**. The FC also contains "Coverages (Geometry-Value Pairs)" 0.1, which is stereotyped «deprecated» in the XMI. | Version numbers in our SMTs must come from one source (the XMI), and this difference must be documented. Consider reporting it to INSPIRE-MIF. |
| G2 | The FC leaves out 20 schemas that are in the XMI: the 16 foundation schemas (GeoSciML, O&M, SWE, WaterML, EarthResourceML), plus **Network** (Generic Network Model), **ElevationTIN**, **Electricity Network** and **Coverages (Domain and Range)**. | The FC can't be the oracle for these schemas. |
| G3 | The FC lists supertypes only if they are inside the FC. All 30 supertype differences are supertypes from Network, Coverages or O&M, e.g. `TransportLink` → `Link`, `SoilThemeCoverage` → `RectifiedGridCoverage`. | For flattening, the FC is incomplete. The XMI is needed. |
| G4 | ShapeChange **misclassifies** `TypeOfProductionBuildingValue` (PF) as "Object Type" because its stereotype is spelled `code list` with a space. Our reader normalises it and treats it as a code list. | An example where our reader is *more correct* than ShapeChange. |
| G5 | Six classes **without a stereotype** (e.g. `DocumentCitation`, `LegislationCitation`, Soil's association class `DerivedProfilePresenceInSoilBody`) are labelled "Object Type" by ShapeChange. | Our reader needs the same default for unstereotyped classes. |
| G6 | Name clash: `MaritimeZone` has **two association roles both named `baseline`** (→ Baseline 1..* voidable; → Shoreline). The FC keeps only the Shoreline one. | A model error. The converter must detect clashes and not silently pick one. |
| G7 | MineralResources and WaterML contain **duplicate associations** (the same role between the same classes twice, e.g. `EarthResource.explorationHistory`, `Mine.relatedActivity`). | Deduplicate, and log it. |
| G8 | The OCL constraints contain errors. AU `AdmininstrativeUnitHighestLevel` refers to `self.loweLevelUnit` (misspelling) and uses `isEmpty` without `()`. | OCL can't be translated automatically into validator rules without manual review. |
| G9 | 5 role differences remain unexplained by any single navigability rule: PF `groupingFacility` (2×) and `groupingInstallation` (marked Unspecified, but absent in the FC); MR `EarthResource.parent` (Non-Navigable, but present in the FC); and the `baseline` clash (G6). | None are in the test themes. Revisit when those themes are in scope. |
